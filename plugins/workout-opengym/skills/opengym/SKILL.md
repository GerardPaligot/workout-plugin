# openGym

Use this optional plugin when the user wants openGym integration. The workout plugin works locally without it. Run Node 20.11 or later. The plugin root is two directories above this skill file. Invoke `node <plugin-root>/skills/opengym/scripts/workout-opengym.mjs --help` for command syntax.

Configure a private instance and profile with a JSON file such as `{"endpoint":"https://gym.example/base","profileId":"verified-user-id","tokenEnv":"OPENGYM_TOKEN","stateDir":"/absolute/private/state","serverTimezone":"Europe/Paris"}`. Set the named environment variable to the token; never put the token in the file. A private or loopback HTTP endpoint also needs `trustedPrivateHttp: true`. Use a private MCP endpoint or equivalent private access for a VPS. For Hermes Docker, make this skill and its bundled CLI available in the container, mount the workout workspace and a persistent state directory, and supply the config and token environment variable. The bundled CLI needs Node 20.11 or later and no runtime npm install.

If a connected workspace or program is moved or reconnected from a legacy configuration, reconnect, sync history, review the history, and adopt the mapping before using program progress or publishing. Do not copy its cached mapping to a different program. Use `connect` to select openGym for a program, `search` to find remote exercises and routines, `adopt` to map a program to existing routines, and `publish` to publish supported plans. A template revision identifies one immutable prescription. Use a new revision when the prescription changes. When known, record `templateId` and `templateRevision` on each occurrence assignment; do not infer a revision for legacy assignments. For publication, construct the payload from the local prescription with verified remote exercise IDs and positive fixed loads. Keep the local prescription authoritative. Do not guess missing or zero loads, ranges, per-side loads, supersets, RIR, or progression; explain unsupported items. Preview writes with `--dry-run`, resolve missing information or mapping conflicts, and use the preview approval and exact proposed data when submitting. For a routine conflict, preview `rebase: true` to review the current phone routine as the new base. Save only with the returned approval and unchanged proposed payload. A user's request to record a workout authorizes the record operation; do not ask for a second confirmation when the preview matches that request.

Use `log` for completed workouts with actual exercises, sets, reps, and loads. If an actual start time is supplied, set `serverTimezone` in the config to the caller timezone, and ensure it matches the MCP process or Docker timezone. The server timezone is a trusted configuration assertion and is checked against the saved record. Never substitute the planned prescription for missing actuals. Ask for missing actuals or save a draft if the CLI supports it. Freestyle workouts are allowed when explicitly requested. Both phone and Hermes workouts count after remote verification. Drafts remain unsynced until verified. Live progress and scheduled completion are not supported.

Use `sync --once` with an explicit date range to refresh verified progress, then `status` to inspect it. Use `history` after sync to inspect bounded cached workout IDs and actuals. Review an unlinked phone workout with the user, then use its ID in `adopt --dry-run` and submit the exact approved mapping. `history` accepts optional `from`, `to`, and `limit` in its input JSON; Its `freshness` can be `observed`, `unconfirmed`, `stale`, or `unresolved`. Only explicitly reviewed, identifiable workouts can be adopted. If sync is unavailable, report cached progress as stale or unknown. A null next session is unknown, not the first session. Never advance local completion pointers from speech, plans, or unmatched workouts.
